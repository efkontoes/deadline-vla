# M0 runbook: go / no-go on real hardware

M0 decides whether the project moves off the laptop. Each check has a command, what "go" means, and what
to do on "no-go". Nothing below has been run yet. The laptop simulator is frozen at `a2754eb` (see
[preregistration.md](preregistration.md)).

| # | Check | Where | Go if |
|---|---|---|---|
| 1 | Isaac Lab 3.0 renders 6 cameras on one drone fast enough | cluster (A100) or an RTX machine | ≥ `drone.ctrl_hz` (10) env steps/s at the top tier |
| 2 | SmolVLA takes 6 views, mixed tiers, dropped views, with image-loop changes only | any GPU ≥ 16 GB | `scripts/m0_smolvla_views.py` exits 0 |
| 3 | Fine-tuning path works end to end | cluster (A100) | loss falls; offline eval runs on all four allocations |
| 4 | Access to a Jetson Orin NX 16 GB or AGX Orin | — | a board you can flash and run TensorRT on |

**Start check 4 today.** It has the longest lead time, and without a board M3 never happens, so the 36%
saving stays synthetic.

## 1. Isaac Lab rendering

```bash
pip install -e .[lerobot]          # plus Isaac Lab 3.0 per NVIDIA's instructions
deadlinevla env-check --config configs/default.yaml --run-dir runs/m0_isaac sim.backend=isaac
```

- `env-check` prints the six-camera step rate and the measured `a_brake` / `tau_track`, and writes
  `env_check_views.png`. Look at that image: six views, correct yaw order, goal object visible.
- **A100 caveat.** Isaac Sim's RTX renderer needs RT cores, which A100s do not have. `sim/isaac_env.py`
  was written against `TiledCamera` with the RTX path. On the A100 nodes, test Isaac Lab 3.0's Newton/Warp
  kit-less tiled rendering instead. If `TiledCameraCfg` cannot select it, the camera block in
  `IsaacDroneEnv._build` is the only part to change; the obs contract (`images`, `depth`, `state`,
  `info`, `privileged`) must stay the same.
- **No-go:** if neither renderer reaches 10 steps/s with six 512 px views, either reduce the top tier for
  M1 or move M1 to an RTX workstation. Record which in the go/no-go log.

## 2. SmolVLA multi-view plumbing

```bash
python scripts/m0_smolvla_views.py --config configs/default.yaml --out runs/m0_smolvla.json
python scripts/m0_smolvla_views.py --config configs/default.yaml --fixed-slots --out runs/m0_smolvla_slots.json
```

- **Go:** all allocations pass (chunk shape (H, 4), finite, the right number of views embedded, finite
  training loss), and **low-tier views produce fewer visual tokens than high-tier ones**. That last check
  is the premise of the whole budget: if SmolVLM pads every view to 512 px, tiers save nothing.
- **Partial go:** only `--fixed-slots` passes. That is the design doc's fallback (six slots, off views
  masked). It is correct but saves no compute; the allocator would then need the vision encoder to run per
  tier outside the model (as `TrtRuntime` does).
- The JSON also gives a first, desktop-GPU latency per allocation. It is not the board table, but if
  latency does not grow with tokens on an A100 either, flag it before M3.

## 3. Fine-tuning path at constant tiers

Record a small dataset at the real tier resolutions with the light simulator, then fine-tune with every
view at the top tier (no allocation randomisation yet; this only checks the training path):

```bash
deadlinevla record --config configs/default.yaml --run-dir runs/m0_train sim.backend=light \
    data.format=lerobot data.episodes=50
deadlinevla train  --config configs/default.yaml --run-dir runs/m0_train sim.backend=light \
    train.alloc_sampler=constant train.constant_tier=3 train.max_steps=2000 train.batch_size=8
```

- **Go:** the loss in `train_log.csv` falls, a checkpoint is written, and `offline_eval.json` has all four
  allocations (it will be poor for the low tiers: the model has not been trained on them yet).
- The light simulator ray-casts 512 px images in numpy, which is slow and memory-hungry (several hundred MB
  per frame across six views). That is fine for 50 episodes; real data comes from Isaac Lab at M2.
- Then repeat with `train.alloc_sampler=mixed` to check that budget-randomised batches (mixed tiers in
  one batch) run; `SmolVLAAdapter.forward_loss` groups samples by allocation for this.

## 4. Jetson board

What to ask for (department, lab, or a vendor loan):

- Jetson **Orin NX 16 GB** (the class VLA-AN flew) or **AGX Orin**; JetPack with TensorRT 10.
- SSH access and the right to install packages; about a week of exclusive use for profiling.
- Then: `deadlinevla export` on the board, `deadlinevla profile` with `serve.runtime=trt`, and set
  `serve.board` to the board's name so `eval` replays the measured table instead of the synthetic one.
